# 结算系统完整业务逻辑梳理

> 代码基线：`E:\wangzhe\wangzhe_project_b\ks`（Laravel + dcat-admin）
> 梳理范围：订单接入 → 佣金计算 → 两阶段自动结算 → 上级抽成/团长分佣 → 售后扣回 → 达人提现审核 → 统计口径
> 说明：下文金额除特别标注外，一律以「分」为单位存储，展示时 `/100` 转为「元」。`cashes.amount` 是例外，按「元」存储。

---

## 一、一句话概括

系统把快手小店的**分销订单**导入后，按「商品的官方分佣率 − 平台 1 个百分点 − 团长比例」算出达人的可分佣比例，再按达人/商品配置拆成**两笔**（首笔、尾笔）在满足时间条件后自动结算；同时支持**上级达人抽成**和**商品团长分佣**；达人端看到的是「已结算 − 已申请提现占用」的可提现余额，运营在后台人工审核提现（确认或驳回），系统自身不对接打款通道。

---

## 二、角色与端

| 角色 | 载体 | 说明 |
|---|---|---|
| 运营/管理员 | `/admin`（dcat `admin` guard） | 配置商品佣金率与团长、审核达人、审核提现、导入订单、看全局统计 |
| 达人（Master） | `/master`（dcat `master` guard，认证模型 `App\Models\Master`） | 拥有若干「分销者/达人号」，看自己的订单、佣金、提现、下级抽成 |
| 分销者 / 达人号（Distributor） | `distributors` 表 | `distributorId` 对应订单里的「CPS 达人 ID」；必须 `status=1`（审核通过）才参与结算 |
| 团长（Leader） | `products.master_id` + `products.leader_rate` | 商品维度的分佣方，按商品抽取固定百分点 |
| 上级达人（Parent） | `masters.parent_id` + `masters.parent_rate` | 从下级达人的佣金里再抽走若干百分点 |

> 分佣链路是三层展开：**订单里的 `distributorId` → `distributors`（status=1）→ `masters`**。任何一层缺失，该订单不会产生佣金，而且界面不报错。后台专门加了「待登记达人」页把漏登记的达人号亮出来（`app/Admin/Controllers/UnregisteredDistributorController.php`）。

## 三、端到端数据流

```
快手小店真实订单
  ├─ 本地 KsSync.exe（驱动 Chrome 拉单）→ xlsx → POST /api/ks/import
  └─ 运营手工上传 → /admin/order/import（单文件）或 /order/import2（多文件）
        │
        ▼
  order_logs（导入批次：店铺、来源 manual/auto、状态、总数/成功/失败）
        │
        ▼
  order_import_YYYY_MM（按月的暂存表，存 Excel 原始行 serialize）
        │  ImportOrder Job（读 Excel → 暂存）
        ▼
  DealImportOrder Job（校验、字段映射、金额转分、按 oid 幂等 upsert orders）
        │
        ▼
  orders + products（按 itemId 自动建商品）+ distributors（按 distributorId 关联）
        │
        │  每 30 分钟：create:run-order-commission
        ▼
  佣金计算（orders.commissionTotal / commission1 / commission2 /
            parent_commission*）+ money 流水 + masters.commission_money
        │
        ▼
  达人端 /master 申请提现 → cashes（status=0 待审核，占用可提现额度）
        │
        ▼
  运营后台批量审核 → cashes.status=1（确认，记 pay_at）或 2（驳回，记 remark）
        │
        ▼
  masters.cash_money 重算（只统计审核通过的提现）
```

补充：
- 视频号订单导入链路（`WechatDealImportOrder`）仍在代码里，但定时抓取「视频号小店订单」的 `app:spider-wechat-order` 已在 `app/Console/Kernel.php:31-34` 停用。
- 老的快手开放平台接口同步命令 `cron:updateOrders` 仍保留，但未加入调度；当前主链路是客户端产表 + 导入。

## 四、数据模型（与结算相关的核心表/字段）

### 4.1 `orders`（订单）

| 字段 | 含义 |
|---|---|
| `oid` | 平台订单号（幂等键，重复导入会覆盖更新） |
| `status` | 订单状态：0 未知 / 10 待付款 / 30 待发货（已付款）/ 40 已发货 / 50 已签收 / 70 订单成功 / 80 订单失败（含交易关闭） |
| `refundStatus` | 退款状态：0 正常；70 退款失败/关闭；其余值都视为售后中 |
| `sendTime` / `payTime` | 发货时间 / 支付时间；**参与分佣的必要条件之一是 `sendTime` 非空** |
| `totalFee` / `expressFee` | 实付款 / 运费（分） |
| `itemId` / `distributorId` | 商品 ID / CPS 达人 ID |
| `sellerType` | 0 快手 / 1 视频号 |
| `commissionTotal` | 预估佣金（达人净得，已扣平台 1%、团长、上级抽成；分） |
| `commission_rate` | 达人净分佣比例（百分点，已扣上级） |
| `commission1` / `commission1_rate` / `commission1Time` | 第一笔佣金 / 比例 / 结算时间 |
| `commission2` / `commission2_rate` / `commission2Time` | 第二笔佣金 / 比例 / 结算时间 |
| `parent_commission` / `parent_commission1` / `parent_commission2` | 上级抽成总额 / 首笔 / 尾笔（分） |
| `cpsPayStatus` | 0 待结算 / 1 第一次已结算 / 2 第二次已结算 / 3 售后 / 4 订单关闭 |
| `importStatus` | 导入批次内处理标记：0 待处理 / 1 第一次结算完成 / 2 第二次结算完成；每次导入重置为 0，结算阶段以 `cpsPayStatus` 为准 |
| `leader_master_id` | 团长 ID（结算时从商品回填） |
| `settlement_dirty` | 结算输入（金额/商品/归属）变更待重算标记；由观察者置 1，主命令处理后清 0 |

### 4.2 `products`（商品）

| 字段 | 含义 |
|---|---|
| `itemId` | 商品 ID（与订单关联） |
| `commissionRate` | 官方预估推广者分佣比例（百分数，如 `21` 表示 21%） |
| `master_id` | 团长 ID；为 0 表示无团长 |
| `leader_rate` | 团长佣金比例（百分点，从商品总佣金里先切走） |

### 4.3 `masters`（达人）

| 字段 | 含义 |
|---|---|
| `rate1` / `rate2` | 快手两笔结算比例（合计应为 100；都为 0 时用系统设置） |
| `wechat_rate1` / `wechat_rate2` | 视频号两笔结算比例（同上） |
| `parent_id` / `parent_rate` | 上级达人 / 上级抽成百分点（0 表示无） |
| `commission_money` | 累计分佣流水余额（分，随 `money` 表增减） |
| `commissioned` / `cashed` / `canCommission` | 缓存字段（元），由每小时任务重算；口径见第八节 |
| `cash_money` | 累计**审核通过**的提现金额（元，decimal 12,2） |

### 4.4 `distributors`（分销者/达人号）

`distributorId`（唯一）、`master_id`、`status`（0 待审核 / 1 通过 / 2 未通过）、`type`（0 快手 / 1 视频号）。

### 4.5 `money`（分佣流水，审计账本）

`oid`、`master_id`、`type`（1 增加 / 2 减少）、`money`、`before_money`、`after_money`、`content`（第一次结算/第二次结算/售后）、`rate`/`rate1`/`rate2`、`parent_rate`、`is_parent`（0 否 / 1 是）、`itemId`（团长分佣时记录商品 ID）。

> `is_parent=1` 同时被两种业务复用：**上级抽成**和**团长分佣**（见问题清单第 1 条）。

### 4.6 `cashes`（提现申请）

`master_id`、`amount`（元，decimal 10,2）、`status`（0 待审核 / 1 确认 / 2 驳回）、`remark`、`apply_at`、`pay_at`、`uuid`（唯一）。

### 4.7 统计表

`chart_masters`（达人按日：有效订单、售后订单、首笔/尾笔佣金、售后金额、提现）、`chart_distributors`（按达人号累计）、`count_of_masters`（达人按日：有效销售额/单数/预估总佣金/剩余佣金/已结算）、`order_statistics`（全局按日佣金汇总）。

> 单位：`chart_masters` 的 `commission1/2/refund_commission` 以「分」存储，`cash` 以「元」存储；后台展示层已统一转成「元」（2026-11-16）。

## 五、订单接入与清洗

### 5.1 两个入口

1. **客户端自动同步**：`POST /api/ks/import`（`app/Http/Controllers/Api/KsImportController.php:28-74`）
   - 入参 `shop_id` + `xlsx`；
   - 校验店铺已在 `sellers` 登记；
   - 文件落 `storage/app/public/imports`；
   - 建 `order_logs`（`source=1` 自动），派发 `ImportOrder`；
   - 回传授权中心「本系统在用哪个店铺」（失败不影响导入）。
2. **运营手工上传**：`/admin/order/import`、`/admin/order/import2`，走同一套 `OrderLog + ImportOrder`（`source` 默认 0 手动）。

### 5.2 两段式处理

- `ImportOrder`：`Excel::import` 按 1000 行/批读入 `order_import_YYYY_MM`，`row` 存 serialize 后的原始行；订单批次状态 4 导入中 → 5 已导入（`app/Jobs/ImportOrder.php`）。
- `DealImportOrder`：逐行反序列化、校验、映射成 `orders`；状态 9 处理中 → 10 已处理 / 11 处理失败（`app/Jobs/DealImportOrder.php`）。

### 5.3 校验与过滤

- 剔除：无支付时间（`row[2]`）或无 CPS 达人 ID（`row[26]`）的行，标记 `type=1`（`DealImportOrder.php:65-70`）。原「未发货剔除」逻辑已注释掉。
- 必填校验：订单号、创建时间、订单状态、实付款、快递费、店铺优惠、平台补贴、主播补贴、成交数量（必须数字）、商品名称/ID/单价、达人 ID、预估佣金、分佣比例（`DealImportOrder.php:220-290`）。
- 金额：`totalFee`/`expressFee`/`discountFee`/`price`/`estimatedIncome` 由「元」字符串 ×100 转成「分」。
- 状态映射：交易关闭/订单失败 → 80；待付款 → 10；已付款/待发货 → 30；已发货 → 40；已收货/已签收 → 50；订单成功/交易成功 → 70；未知 → 0（`DealImportOrder.php:298-314`）。
- 退款状态映射：见 `DealImportOrder.php:322-345`；「退款失败/退款关闭」→ 70，视为正常。
- 发货时间：用正则从 `row[43]` 提取 `YYYY-MM-DD HH:MM:SS`，匹配不到则 `null`（`DealImportOrder.php:112-116`）。
- 商品：`itemId` 不存在则自动建 `products`（佣金率默认 0，需运营后配）。
- 达人：按 `distributorId` 查 `Distributor`，昵称优先用已有档案。

### 5.4 幂等与覆盖

- `Order::updateOrCreate(['oid' => ...])`（`DealImportOrder.php:119-146`）：同一订单重复导入会覆盖业务字段。
- **每次导入都把 `importStatus` 置回 0**（`DealImportOrder.php:143`）；它只是导入批次内的处理标记，首/尾笔不再用它做闸门（2026-11-16）。
- **结算输入变化会标记重算**：`totalFee/expressFee/itemId/distributorId/sellerType` 变化且订单已有佣金时，`OrderObserver` 置 `settlement_dirty=1`；主命令 `recalcDirtyOrders()` 冲正旧账本后按当前数据重结（2026-11-16）。
- 订单字段变更审计：`OrderObserver` 只记录业务字段（状态、退款状态、时间、金额、分佣率、达人等），不记录佣金计算中间字段；来源分「手工/自动导入/系统任务」，写入 `order_histories`（`app/Observers/OrderObserver.php:19-31`）。

### 5.5 常见漏结算原因

- `distributors` 未登记或 `status<>1`；
- `products.commissionRate=0`（商品未配置佣金率）；
- `sendTime` 为空（客户端需补抓订单详情才能拿到发货时间，见 `docs/发货时间与分佣打通.md`）；
- 订单状态不在 30/40/50/70，或退款状态不是 0/70。

## 六、佣金计算规则

### 6.1 资格条件（`Order::scopeOfCommission`，`app/Models/Order.php:298-306`）

一笔订单要参与分佣，必须同时满足：

1. `status ∈ {30, 40, 50, 70}`（已付款/已发货/已签收/订单成功）；
2. `refundStatus ∈ {0, 70}`（正常或退款失败/关闭）；
3. `sendTime` 非空；
4. 关联 `product` 存在且 `commissionRate > 0`；
5. 订单的 `distributorId` 能匹配到 `status=1` 的 `distributors`，且该分销者属于某位 `master`。

> `Order::getIsRateAttribute`（界面上的「是否分佣」）只看状态、退款状态、商品佣金率，**不看 `sendTime`**，所以可能与实际结算范围不一致。

### 6.2 比例定义（百分点，分母是订单实付减运费）

设：

- `B = totalFee - expressFee`（分）
- `R = products.commissionRate`（百分数，如 21 表示 21%）
- `L = products.leader_rate`（团长比例，仅当 `products.master_id != 0` 时生效）
- `P = masters.parent_rate`（上级抽成百分点，仅当 `parent_id` 与 `parent_rate` 都有值）

先扣平台固定 1 个百分点（导出表头写明「分销率(官方佣金率1%)」）：

```
达人可分佣总比例 rate = R - 1 - L
达人净得比例         = rate - P
上级抽成比例         = P
团长分佣比例         = L
```

四个角色加起来正好覆盖 `R - 1`：`(rate - P) + P + L = R - 1`。

### 6.3 两笔拆分

两笔比例 `s1 / s2` 的来源优先级：

1. 达人自身 `rate1 + rate2`（两者之和非 0 时使用；视频号用 `wechat_rate1 + wechat_rate2`）；
2. 否则用系统设置 `commission1_rate / commission2_rate`（默认 50/50；视频号用 `wechat_commission1_rate / wechat_commission2_rate`）。

金额计算（`app/Console/Commands/OrderCommission.php`）：

```
达人总佣金        commissionTotal      = int(B × rate / 100)            （有上级时 rate 换成 rate - P）
上级总抽成        parent_commission    = int(B × P / 100)
首笔前先拆上级：
  parent_rate_stage = P × s1 / 100
  commission1      = int(B × (s1 - parent_rate_stage) / 100)
  parent_commission1 = int(B × parent_rate_stage / 100)
尾笔：
  commission2      = commissionTotal - commission1
  parent_commission2 = parent_commission - parent_commission1
```

团长（独立于达人/上级，记到 `products.master_id`）：

```
leader_rate1 = L × s1 / 100
leader_rate2 = L × s2 / 100
团长首笔     = int(B × leader_rate1 / 100)
团长尾笔     = int(B × leader_rate2 / 100)
```

> 团长两笔、上级首笔的拆分比例都使用**出单达人所在 master 的渠道结算比例**：快手用 `rate1/rate2`（或全局 `commission1_rate/2_rate`），视频号用 `wechat_rate1/2`（或全局 `wechat_commission1_rate/2_rate`）。团长自己的比例配置不参与这里。
>
> 2026-11-16 修复：上级首笔也走同一条 `stage1_percent` 口径；之前固定用快手 `master->rate1`，视频号订单会和达人首笔拆分不一致。
>
> 上级抽成有上限兜底：`effectiveParentRate = min(parent_rate, order.rate)`；超过订单净分佣率时按订单费率封顶（2026-11-16）。

### 6.4 数值示例

假设：`B = 9,990 分`，`R = 5`（5%），无团长、无上级，达人 `rate1=rate2=50`。

```
rate             = 5 - 1 = 4
commissionTotal  = int(9990 × 4 / 100) = 399 分（¥3.99）
commission1      = int(9990 × 2 / 100) = 199 分（¥1.99）
commission2      = 399 - 199 = 200 分（¥2.00）
```

加入团长 `L=2`：`rate = 5-1-2 = 2`，达人总佣金 `199 分`；团长首笔 `int(9990×1/100)=99 分`、尾笔 `99 分`。
加入上级 `P=10`（设 `R=21`）：`rate=20`，达人总佣金 `1000 分`，上级总抽成 `1000 分`；首笔达人 `500`、上级 `500`，尾笔各 `500`。

### 6.5 配置优先级与校验

| 配置 | 位置 | 校验/说明 |
|---|---|---|
| 两笔比例 | 达人 `rate1/rate2`、`wechat_rate1/rate2` | `rate1` 与 `rate2` 都非 0 时必须合计 100，否则报错（`app/Admin/Controllers/MasterController.php:169-175`）；只设一个时直接采用 |
| 商品分佣率 | `products.commissionRate` | 运营在商品列表直接编辑；变更会触发重算任务 |
| 团长 | `products.master_id` + `leader_rate` | `leader_rate ≤ commissionRate - 1`，否则报错（`app/Admin/Controllers/ProductController.php:156-162`） |
| 上级 | 达人列表「添加下级」 | 下级必须尚无上级；不能把当前上级加成下级；同时设置 `parent_rate`（`app/Admin/Forms/AddMasterChild.php:20-45`） |
| 结算时间 | `admin_setting` | `commission1_days` 默认 72 小时；`commission2_days` 默认 600 小时 |

## 七、结算任务与状态机

### 7.1 调度

`app/Console/Kernel.php`：

| 频率 | 命令 | 作用 |
|---|---|---|
| 每 30 分钟 | `create:run-order-commission` | 把 `create:order-commission` 丢进队列，执行核心分佣 |
| 每小时 | `create:update-master-commission` | 重算 `masters.commissioned/cashed/canCommission` |
| 每天 01:00 | `create:run-chart-master` | 重算近约 25 天 `chart_masters` + `chart_distributors` + 当日 `count_of_masters` |
| 每天 02:00 | `create:order-statistics` | 全局佣金汇总 |
| 每天 03:00 | `create:run-count` | 重算近 30 天 `count_of_masters` |
| 每 10 分钟 | `client:health-check` | 客户端/队列健康巡检（与结算无关） |

### 7.2 `create:order-commission` 的八个步骤

`app/Console/Commands/OrderCommission.php`：

1. **`refundToNotRefund()`**
   - 找 `refundStatus ∈ {0,70}` 且 `cpsPayStatus=3` 的订单（即售后又恢复正常的）；
   - 把 `cpsPayStatus` 置 0，`commissionTotal/1/2`、`commission_rate/1_rate/2_rate`、`parent_commission*` 清零；
   - 同时重置 `importStatus=0`、`leader_master_id=0`、`commission1Time/2Time=null`，让订单在同一轮命令里重新计算并结算（2026-11-16 修复）；
   - 不直接反向流水：售后扣回时已按实际入账净额冲回。
2. **`closedToNormal()`**：找 `cpsPayStatus=4`（订单关闭）且 `status` 回到 30/40/50/70、`refundStatus ∈ {0,70}` 的订单，重置结算字段，让主流程重新结算。
3. **`recalcDirtyOrders()`**：处理 `settlement_dirty=1` 的订单；对未售后且 `cpsPayStatus` 0/1/2 的订单按账本净额冲回、重置结算字段，后面的步骤会按当前数据重算；售后中/已售后/已关闭的订单不在这里冲正。
4. **`commisson()`**：对每个达人名下、`commissionTotal=0` 的订单，算 `commissionTotal` 与 `parent_commission`、`commission_rate`。
5. **`firstCommisson()`**：条件满足时结第一笔。
6. **`secondCommisson()`**：条件满足时结第二笔。
7. **`refund()`**：对已结算（`cpsPayStatus` 1/2）且当前处于售后的订单扣回，不再依赖 `importStatus`；处理后置 `cpsPayStatus=3`，重复执行不会重复扣。
8. **`close()`**：只处理已结算（`cpsPayStatus` 1/2）且 `status ∈ {0,80}`、`refundStatus ∈ {0,70}` 的订单，按账本净额冲回并置 `cpsPayStatus=4`；未结算订单不动。

### 7.3 首笔结算条件（全部满足）

- `ofCommission()`（见 6.1）；
- `commission1 = 0` 且 `commission2 = 0`；
- `sendTime <= now() - commission1_days 小时`（默认 72 小时，按发货时间起算）。

写入：`cpsPayStatus=1`、`commission1`、`commission1_rate`、`parent_commission1`、`commission1Time`，并生成达人（及上级、团长）的 `money` 流水。

### 7.4 尾笔结算条件（全部满足）

- `ofCommission()`；
- `status = 70`（订单成功）；
- `commission2 = 0`；
- `sendTime <= now() - commission2_days 小时`（默认 600 小时，按发货时间起算）。

写入：`importStatus=2`、`cpsPayStatus=2`、`commission2`、`commission2_rate`、`parent_commission2`、`commission2Time`，并生成流水。

> 2026-11-16 修复：首/尾笔等待期统一按 **`sendTime`（发货时间）** 起算，与后台「结算设置」文案和 `SettingsController` 的「订单结算以发货时间计算」一致；`scopeOfCommission` 仍要求 `sendTime` 非空。

### 7.5 状态机

```
cpsPayStatus
  0 待结算 ──首笔──▶ 1 第一次已结算 ──尾笔──▶ 2 第二次已结算
       │                    │
       │                    ├──发生售后──▶ 3 售后
       │                    └──订单关闭(0/80)──▶ 4 订单关闭
  3 售后 ──退款状态恢复(0/70)──▶ 0 待结算（refundToNotRefund）
  4 订单关闭 ──订单重新有效(30/40/50/70)──▶ 0 待结算（closedToNormal）
```

> `cpsPayStatus=4` 只对已结算（1/2）的订单生效；未结算的 `status=0/80` 保持待结算，没有佣金可扣。

`importStatus`：0 待处理 / 1 第一次结算完成 / 2 第二次结算完成；首笔写 1、尾笔写 2，售后保留当前阶段。它只是导入批次内标记（每次导入重置为 0），结算阶段以 `cpsPayStatus` 为准。

### 7.6 流水账本

- 每次结算按「达人 / 上级 / 团长」分别写 `money` 行，同时原子增减 `masters.commission_money`。
- `type=1` 增加、`type=2` 减少；`content` 为「第一次结算」「第二次结算」「售后」「订单关闭」。
- 团长流水带 `itemId`（商品 ID）；`is_parent=1`。
- 团长流水由 `syncLeaderMoneyLog` 按该订单/团长/商品的已入账净额调整到目标金额（首笔目标 = 首笔金额，尾笔目标 = 两笔累计；售后只冲回实际净额），重跑不会重复记账。
- **上级抽成流水**：2026-11-15 起改为按订单 `parent_commission1/2` 的目标金额做差额记账（`syncParentMoneyLog`），与订单字段一致；旧版历史流水仍可能少记，退款按该订单实际入账净额冲回，不会再扣成负数。

### 7.7 重算/重置工具

| 命令 | 行为 |
|---|---|
| `create:run-order-commission clear` | **清空 `money` 表**；把全部订单 `importStatus/cpsPayStatus/佣金字段` 归零；把 `masters.commission_money` 归零，然后重新入队（`RunOrderCommission.php:32-53`） |
| `create:show-order-commission {oid}` | 同样是「清空流水 + 全量重置 + 全量重算」，调试用（`ShowOrderCommission.php:30-67`），**不要在生产随手执行** |
| 商品佣金率变更 | `Product` 模型 `updated` 监听 `commissionRate` 脏值，派发 `OrderCommissionByProduct`（`app/Models/Product.php:34-39`） |

`OrderCommissionByProduct`（2026-11-16 重写）不再复制首/尾笔计算：它把该商品下未售后、`cpsPayStatus` 0/1/2 的订单按 `money` 实际入账净额冲回，重置佣金/上级/团长/结算状态，然后排队主命令 `create:order-commission` 按新费率完整重算并重新结首/尾笔。售后订单（`cpsPayStatus=3`）不动。

## 八、售后与反向结算

### 8.1 判定

- 售后订单 = `refundStatus ∉ {0, 70}`（`Order::scopeOfRefund`）。
- 售后扣回只处理：`cpsPayStatus ∈ {1, 2}` 且当前处于售后的订单，不再依赖 `importStatus`。

### 8.2 扣回动作（`OrderCommission::refund()`）

- 订单：`cpsPayStatus=3`；`importStatus` 保留当前结算阶段（1 或 2）；
- 达人：扣 `commission1 + commission2`；
- 上级：扣该订单实际记入上级账本的净额（新数据等于 `parent_commission1 + parent_commission2`；历史少记则按实际）；
- 团长：扣该订单实际记入团长账本的净额（首笔后发生售后只扣首笔，不再按全额 `leader_rate` 多扣）。

### 8.3 需要特别注意的机制

1. **售后扣回不再依赖导入批次（2026-11-16 修复）**：`refund()` 现在只按 `ofRefund() + cpsPayStatus ∈ {1,2}` 判断，不再要求 `importStatus=0`；处理后置 `cpsPayStatus=3`，重复执行不会重复扣。
2. **售后恢复会重新进入结算（2026-11-16 修复）**：`refundToNotRefund()` 现在同时重置 `importStatus=0`、`parent_commission*`、`leader_master_id`、结算时间，订单会在同一轮命令里重新计算并结首/尾笔，不再卡在「待结算」。
3. **数据源仍是前提（2026-11-16 调整）**：`refund()` 能扣回的前提是订单的 `refundStatus` 已经更新到库。客户端已将 `refresh_window_days` 设为 0，L3 从 `history_start_date` 全量回刷；超过 45 天的旧订单退款也会在后续全量轮次入库。若客户端未运行或回刷失败，仍需补导/补数。
4. **订单关闭（status 0/80）扣回（2026-11-16 修复）**：只处理已结算（`cpsPayStatus` 1/2）且 `refundStatus ∈ {0,70}` 的订单；按账本净额冲回达人/上级/团长并置 `cpsPayStatus=4`。未结算订单没有佣金可扣，不动。订单重新变为 30/40/50/70 且退款正常时，`closedToNormal()` 重置后重新结算。

## 九、提现（Cashes）

### 9.1 可提现金额公式（实时，`CashTrait::canCommission`）

```
可提现 = 自己名下（status=1 分销者）订单已结算佣金
         （commission1 + commission2，cpsPayStatus ∈ {1,2}）
       + 下级达人订单的上级抽成
         （parent_commission1 + parent_commission2，cpsPayStatus ∈ {1,2}）
       + 团长分佣流水净额
         （money: is_leader=1, type=1 之和 − type=2 之和）
       − 已占用提现
         （cashes: status ∈ {0,1}，即待审核 + 已确认）
```

相关方法（`app/Traits/CashTrait.php`）：

- `firstCommission/secondCommission`（20-41）：已结算的两笔；
- `commissioned`（119-125）：两者相加；
- `parentCommissioned`（157-163）：下级订单的上级抽成；
- `leaderCommissioned`（393-408）：`money.is_leader=1` 的团长流水净额（2026-11-15 修复后只统计团长；上级抽成由 `parentCommissioned` 按订单计算）；
- `cashed`（199-207）：待审核 + 已确认的提现；
- `canCommission`（368-388）：上面的组合；
- `canCommissionExcludeCashId`（416-438）：编辑某条提现时排除自身。

### 9.2 申请（达人端）

- 入口：达人端数据面板「可提现金额」卡片 → 弹窗表单（`app/Master/Forms/Cash.php`）。
- 校验：金额非空、>0、≤ 实时 `canCommission`；否则报错。
- 写入：`cashes`，`status=0`、`apply_at=now()`、`uuid` 唯一。
- 达人端提现列表只读（`app/Master/Controllers/CashController.php` 关闭了所有编辑/删除/新建）。

### 9.3 审核（运营端）

- 批量：`AuditCash` 表单（`app/Admin/Forms/AuditCash.php`）
  - `status=1` 确认：**先按当前可提现额复核**（2026-11-16）。按达人分组，`可提现 = canCommission(master) + 本次选择中 status=0 的占用`，与本次要确认的合计比较；任一组不足则整批不确认，返回达人、可提现、本次合计和记录 ID；
  - `status=2` 驳回：写 `remark`；`status=0` 退回待审核；
  - 已确认（`status=1`）的记录不能再次被批量更新（`where status <> 1`）。
- 审核完成后重算 `masters.cash_money` = 该达人所有 `status=1` 的提现之和（由 `CashAudit` 服务统一处理）。
- 运营也可以直接新增/编辑提现记录（`app/Admin/Controllers/CashController.php`）：
  - 新建/编辑待审核或确认记录时校验金额 ≤ 当前可提现（编辑时排除自身）；
  - 驳回/退回待审核不校验金额；
  - 保存后重算 `cash_money`。

### 9.4 占用与释放

- `status=0`（待审核）和 `status=1`（确认）都占用可提现额度；
- `status=2`（驳回）立即释放；
- 提现记录不支持达人端撤销，运营端也没有删除入口。

### 高（资金安全）

1. **上级抽成被重复计入，且上级流水金额与订单字段不是同一套公式（可导致上级可提现为负，已修复）**
   - 订单口径：`parent_commission = B × parent_rate / 100`（百分点）；首笔 `parent_commission1 = B × (parent_rate × master.rate1 / 100) / 100`。
   - 流水口径：给上级写 `commission / (1 - parent_rate / 100) - commission`（`OrderCommission.php:183-186`），是按「下级佣金的百分比」算，不是按 GMV 的百分点算。实测同一笔订单：订单 `parent_commission1=500 分`，上级流水只记 `44.44 分`。
   - `leaderCommissioned()` 又把所有 `money.is_parent=1` 的流水（上级抽成 + 团长分佣）加进可提现（`CashTrait.php:393-408`），而 `canCommission()` 已经通过 `parentCommissioned()` 按订单加过一次上级抽成（`CashTrait.php:377`）。
   - 正常订单：上级可提现 = 订单抽成 10.00 + 流水抽成 0.88 = 10.88（正确 10.00，多 0.88）。
   - 子单退款后：退款按订单字段全额扣 10.00，但流水只记过 0.88，`leaderCommissioned(parent)` 变为 -9.11，`canCommission(parent)` 也变为 -9.11；上级的正常提现会被卡住，`commission_money` 同步变负。
   - 复审：已用真实命令端到端复现（见「复审记录」）。
   - 修复（2026-11-15）：上级流水改为按订单 `parent_commission*` 的目标金额做差额记账（`syncParentMoneyLog`）；团长流水新增 `is_leader=1` 独立标记，`leaderCommissioned` 只统计团长；退款按该订单实际入账净额冲回。修复后验证见第十六节。

### 中高（条件性 / 口径一致性）

2. **尾笔结算后的售后，修复前只有订单再次被导入才会扣回（已修复）**
   - 修复前 `refund()` 只处理 `importStatus=0`，而尾笔结算把 `importStatus` 置 1；只有再次导入（`DealImportOrder` 重置为 0）才会扣回。

## 十四、端到端时间线示例

以一笔快手订单为例：

```
D0 10:00  付款（payTime），订单状态 30，发货时间已补抓到（sendTime 非空）
D0        商品 commissionRate=21，leader_rate=0，达人 rate1/rate2=50/50，无上级
          B = 10,000 分 → rate=20 → commissionTotal=2,000 分（¥20）

D0+72h    首笔结算任务命中（sendTime + 72h；假设 D0 当天发货）
          commission1 = 1,000 分 → money +1000，commission_money +1000
          cpsPayStatus=1

D0+25d    订单状态变为 70，且 sendTime + 600h 已满足
          commission2 = 2,000 − 1,000 = 1,000 分 → money +1000
          cpsPayStatus=2，importStatus=1

达人端    已结算 2,000 分；提出提现 2,000 分
          cashes(status=0) 占用 2,000 分，可提现余额归零
          运营确认 → status=1，pay_at 记录，cash_money += ¥20（系统不实际打款）

若尾笔后发生退款：
          refundStatus 变为非 0/70 → ofCommission 排除该单 → 达人可提现额立即下降
          退款状态入库后，下一轮结算即扣回（不再要求再次导入），cpsPayStatus=3
          团长按该订单实际入账净额冲回（首笔后退款只扣首笔）
```
